Bring in a statement

One drop zone, four file shapes. A PDF goes through page selection and column mapping; a CSV or spreadsheet skips straight to mapping; JSON takes its own path. Nothing reaches the journal from here — this stage ends at a staged batch.

Drop statements here or choose files — several at once is fine, they queue PDF CSV XLS / XLSX JSON OFX
Every file in the queue is read against this account. A statement whose own letterhead names a different account is held, not imported.
Files are read on this machine. A statement listing every payment you have made in three years is not sent anywhere, and a PDF password is used to open the file and then discarded.

Which pages hold the table

A PDF has no rows and no columns — it has glyphs at coordinates. Before anything can be mapped, the cover page, the repeated letterhead, the page footers and the terms page have to come out, and the opening and closing balance blocks have to be told apart from transactions.

Page preview

The preview is the page as the file draws it. A wrong region is visible rather than inferred.

Page selection is not cosmetic. A terms-and-conditions page read as a table is where phantom rows come from, and a footer line caught inside the table is where a balance check that should have failed quietly passes. Both are silent, so both are chosen here rather than guessed later.

Three independent checks, in rising strength: every row against the balance printed beside it, the parsed totals against the totals the bank printed outside the table, and every row against what is already in the journal. They are shown separately because they fail separately.

JSON takes a different route

A JSON export has no pages, no columns and no printed balance to check against. What it has instead is a shape — and the two questions worth asking are where the transaction array lives and what each key means. Everything after that rejoins the same pipeline.

Shape

Valid JSON, UTF-8, 41,208 bytes, one root object.
Three arrays of objects found. The one with a date-like and an amount-like key on every element is the candidate.
Amounts are objects, not numbers: {"value": "-486.00", "currency": "INR"}. A nested path is needed.
No running balance anywhere in the file. The parse cannot be checked against itself, and the batch will carry UNVERIFIED rather than a false pass.

Where intake ends

Everything before this line is about reading a file correctly. Everything after it is about deciding what the rows mean. They are different jobs with different failure modes, and this is the one place where the first hands over to the second.

Stages 1–5 · this artifact

Intake

Opens the file, picks the pages, assigns the columns, reads the dates and amounts, proves the reading against the bank’s own figures, and asks the journal whether it has seen these rows before.

Fails like this
The wrong column was read as the amount.
A date read MM/DD when it was DD/MM.
A terms page was read as 40 phantom rows.
Staged rows
/imports/[batchId] · existing screen

Review

Categorises, resolves duplicates, picks the other side of each transfer, confirms, and posts. Owns the review table, the keyboard-first bulk confirm and the original-document pane.

Fails like this
A card payment categorised as an expense instead of a transfer.
A real second payment dismissed as a duplicate.

What crosses

One import_batches row, N import_rows

And what does not

The mapping. It is saved as a format, referenced by formatId. The batch records which format read it, not the rules themselves, so one correction fixes every future statement rather than one batch.
The file bytes. The original goes to the document archive and the batch keeps only fileHash. The review screen’s document pane reads the archive, not the batch.
The PDF password. Used to derive the decryption key, held nowhere.
Any category decision. Keyword rules fire during staging and write parsedJson.suggestedAccountId, but the choice belongs to review.
Anything in the ledger. No posting exists until review posts the batch.

The contract, in one line each

Intake promises that rawJson is the source line verbatim, so a re-parse never needs the original upload back.
Intake promises that amount is positive and direction carries the sign, matching Posting. A signed amount would make −500 ambiguous between a withdrawal and a reversed deposit.
Intake promises that a row it could not read arrives as a problem with a reason, never as a row worth zero.
Review promises that a row whose trust is BROKEN or whose controls are MISMATCHED still shows the warning on its own screen. Intake’s verdict does not expire at the boundary.
Neither owns the duplicate decision. Intake flags with a layer; review decides.
